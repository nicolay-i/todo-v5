# План реализации единого интерфейса серверных функций (RPC слой)

## 1. Цель
Унифицировать обращение фронта к серверным бизнес‑операциям через единый RPC endpoint вида: `{ method: string; params: object }` с типобезопасностью (общие TypeScript интерфейсы) и сохранением инварианта: любая мутация возвращает целостный `TodoState`.

## 2. Принципы
1. Все бизнес‑операции продолжают жить в `todoService.ts` (единая точка логики).
2. Диспетчер на сервере только:
	 - Парсит тело
	 - Валидирует `method` и `params`
	 - Вызывает соответствующую функцию сервиса
	 - Формирует единый ответ
3. Фронт вызывает `rpc(method, params)` вместо набора REST роутов.
4. Типы методов / параметров / ответов — одна декларация, импортируемая и на фронте, и на бэке.
5. Ошибка не роняет инварианты: в ошибках возвращаем актуальный `TodoState` (как и сейчас).

## 3. Структура типов
Новый файл: `src/lib/rpcTypes.ts`.

```ts
// Категории
export type RpcMethod =
	| 'todo.add'
	| 'todo.rename'
	| 'todo.toggleCompleted'
	| 'todo.move'
	| 'todo.togglePinned'
	| 'todo.delete'
	| 'tag.add'
	| 'tag.update'
	| 'tag.delete'
	| 'tag.attach'
	| 'tag.detach'
	| 'pinnedList.create'
	| 'pinnedList.update'
	| 'pinnedList.delete'
	| 'pinnedList.setActive'
	| 'pinnedTodo.move'
	| 'state.replace'
	| 'random.todo' // пример read-операции
	| 'auth.telegramLogin' // опционально
;

// ParamsMap: для каждой операции — строгий контракт
export interface RpcParamsMap {
	'todo.add': { parentId?: string | null; title: string; alias?: string | null }; // позиционирование = 0
	'todo.rename': { id: string; title: string; alias?: string | null };
	'todo.toggleCompleted': { id: string };
	'todo.move': { id: string; targetParentId: string | null; targetPosition: number };
	'todo.togglePinned': { id: string };
	'todo.delete': { id: string };
	'tag.add': { name: string };
	'tag.update': { id: string; name: string; position?: number };
	'tag.delete': { id: string };
	'tag.attach': { todoId: string; tagId: string };
	'tag.detach': { todoId: string; tagId: string };
	'pinnedList.create': { title: string; isPrimary?: boolean };
	'pinnedList.update': { id: string; title?: string };
	'pinnedList.delete': { id: string };
	'pinnedList.setActive': { id: string };
	'pinnedTodo.move': { todoId: string; fromListId: string; toListId: string; toPosition: number };
	'state.replace': { state: unknown }; // сырой импортируемый JSON, нормализация внутри
	'random.todo': { tagIds?: string[]; includeCompleted?: boolean };
	'auth.telegramLogin': { authData: unknown }; // пример
}

// Возвраты: мутации -> всегда полный TodoState; чтения -> данные + состояние (если нужно)
import type { TodoState, Todo } from './types';

export interface RpcReturnMap {
	'todo.add': { state: TodoState };
	'todo.rename': { state: TodoState };
	'todo.toggleCompleted': { state: TodoState };
	'todo.move': { state: TodoState };
	'todo.togglePinned': { state: TodoState };
	'todo.delete': { state: TodoState };
	'tag.add': { state: TodoState };
	'tag.update': { state: TodoState };
	'tag.delete': { state: TodoState };
	'tag.attach': { state: TodoState };
	'tag.detach': { state: TodoState };
	'pinnedList.create': { state: TodoState };
	'pinnedList.update': { state: TodoState };
	'pinnedList.delete': { state: TodoState };
	'pinnedList.setActive': { state: TodoState };
	'pinnedTodo.move': { state: TodoState };
	'state.replace': { state: TodoState };
	'random.todo': { todo: Todo | null; state: TodoState };
	'auth.telegramLogin': { state: TodoState; userId?: string };
}

// Обёртки
export type RpcRequest<M extends RpcMethod = RpcMethod> = {
	method: M;
	params: RpcParamsMap[M];
};

export type RpcSuccess<M extends RpcMethod> = {
	ok: true;
	method: M;
	data: RpcReturnMap[M];
};

export type RpcError = {
	ok: false;
	error: string;
	// Актуальное состояние, если удалось извлечь
	state?: TodoState;
};

export type RpcResponse<M extends RpcMethod = RpcMethod> = RpcSuccess<M> | RpcError;
```

## 4. Backend: /api/rpc
Файл: `src/app/api/rpc/route.ts`.

Алгоритм:
1. Проверить метод запроса: только POST.
2. `await request.json()` -> верифицировать форму `{ method, params }`.
3. Проверить что `method` ∈ `RpcMethod`.
4. Опционально runtime-валидация `params` через Zod (минимум — структурные поля).
5. Определить «мутация» или «чтение» (можно через Set).
6. Вызвать соответствующий хендлер-адаптер, который делегирует в `todoService.ts`.
7. Поймать ошибки, извлечь текущее состояние (`getTodoState()`) и вернуть `RpcError`.
8. Успех: упаковать `RpcSuccess`.

### Производительность
Мутации уже атомарны; диспетчер не ломает батч‑операции (позиционирование и т.п.). Возможное расширение: поддержка массива `requests: RpcRequest[]` для последовательного применения внутри одной транзакции (future phase).

## 5. Адаптеры в todoService
Вместо переписывания логики — тонкие функции соответствующие карте методов:
```ts
export async function rpcHandlers() {
	return {
		'todo.add': (p) => addTodo(p.parentId ?? null, p.title, p.alias ?? null),
		'todo.rename': (p) => renameTodo(p.id, p.title, p.alias ?? null),
		// ... и так далее
		'random.todo': (p) => getRandomTodo(p.tagIds, p.includeCompleted),
	};
}
```
Либо константа `const RPC_HANDLERS: Record<RpcMethod, (params:any)=>Promise<RpcReturnMap[RpcMethod]>>`.

## 6. Frontend клиент
Добавить в `apiClient.ts`:
```ts
export async function rpc<M extends RpcMethod>(method: M, params: RpcParamsMap[M]): Promise<RpcResponse<M>> {
	const res = await fetch('/api/rpc', {
		method: 'POST',
		headers: { 'Content-Type': 'application/json' },
		body: JSON.stringify({ method, params }),
	});
	return res.json();
}
```
`TodoStore` при мутациях вызывает `rpc(method, params)` → при `ok` делает `replaceState(data.state)`; при ошибке — также `replaceState(error.state)`.

## 7. Миграция
Этапы:
1. Создать типы и endpoint (параллельно со старыми роутами).
2. Обновить `TodoStore` мутации на RPC; затем компоненты.
3. Оставить legacy REST ещё одну итерацию (фича‑флаг / переключатель), затем удалить.
4. Удалить неиспользуемые файлы роутов (`/api/todos`, `/api/tags`, `/api/pinned-lists`, если полностью покрыты RPC).

## 8. Тестирование
1. Юнит тесты диспетчера: неизвестный метод, корректный метод, ошибка сервиса.
2. Интеграционный тест: цепочка мутаций (add → rename → move) сохраняет инварианты.
3. Snapshot ответов `RpcSuccess` на ключевые операции.

## 9. Ошибки и валидация
Ключевые случаи:
- Неизвестный метод → 400 + `{ ok:false, error:'UNKNOWN_METHOD', state }`.
- Неверные параметры → 400 + `INVALID_PARAMS`.
- Нарушение глубины дерева → маппинг текущей ошибки в `error:'DEPTH_LIMIT'`.
- Нарушение уникальности `active/primary` — сервис обязан сам корректировать; наружу не выбрасывать расхождение.

## 10. Расширения (после MVP)
1. Batch RPC: `{ batch: RpcRequest[] }` (транзакционный пакет).
2. SSE / WebSocket push обновления состояния для multi‑client.
3. Codegen OpenAPI / JSON Schema из `RpcParamsMap`.
4. Versioning: `method` как `todo.add@v1` для эволюции контрактов.

## 12. Риски
- Разнобой имен: фиксируем naming convention `domain.action`.
- Разрастание params: нужен линтер / подсветка, поддержка документации.
